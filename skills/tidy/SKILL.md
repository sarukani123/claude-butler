# 記憶の整理（案を作るだけ）

バトラーの記録は、会話のたびに追記されて増えていく。このスキルは全体を見直し、**整理の案**を作る。
反映は利用者の承認後に、通常の会話で行う。ここでは記録を書き換えない。

## 手順
1. 今のフォルダに `CLAUDE.md` と `profile.md` が無ければ、「バトラーの拠点ではないようです。拠点は `/butler:init` で作れます」と伝えて止まる。
2. Git 管理でリモートがあれば `git pull` で最新にする。
3. `tidy/learnings.md` があれば読む（過去の採否から分かった利用者の傾向。案の出し方に反映する）。
4. `tidy/` に未処理の案（「状態：承認待ち」のもの）が残っていれば、新しい案は作らずに、その案を見てほしいと伝えて終える。案を溜めないため。
5. 次のファイルを読む：`profile.md`、`waiting-on-you.md`、`open-items.md`、`projects.md`、`journal/` のすべて、`knowledge/` のすべて。
6. 下の「見る点」に沿って候補を洗い出し、効果の大きい順に **最大 10 件** に絞る。
7. 候補が 1 件もなければ、何も書かずに「いまは整理の必要がありません」と伝えて終える。
8. `tidy/proposal-YYYY-MM-DD.md`（実行日）に案を書く。同じ日の案が既にあれば `-2` などを付ける。
9. Git 管理なら `記憶の整理案（YYYY-MM-DD）` というメッセージでコミットし、リモートがあれば push する（CLAUDE.md の同期のルールに従う）。
10. 利用者に件数と見出しを短く伝え、「番号ごとに 採用／見送り を教えてください」と頼む。

## 見る点
- **片付いたのに残っているもの**：waiting-on-you・open-items・projects の中で、journal から完了や決着が読み取れる項目。日付が過ぎた予定。
- **食い違い**：同じ事柄について、ファイル同士や新旧の記録で内容が違うもの（例：journal で訂正されたのに profile が古いまま）。
- **反映漏れ**：journal に出てきた好み・判断・環境の変化のうち、profile や knowledge に入っていないもの。
- **重複**：同じことが複数の場所に書かれていて、一か所にまとめた方がよいもの。
- **長すぎるもの**：古い journal（目安：2 週間以上前）の要点を `journal/summary.md` にまとめる案。まとめる文案も書く。
- **古くなった知見**：knowledge のうち、確認日から 3 か月以上たち、料金・提供状況など変わりやすい内容を含むもの。再確認を勧める。

## 案の書き方
```
# 記憶の整理案（YYYY-MM-DD）
状態：承認待ち

## 1. <一言で>
- 対象：<ファイル名と該当箇所>
- 今：<現状を短く>
- 案：<どう直すか。追記・削除する文があればその文案>
- 理由：<なぜ。根拠の journal の日付など>
- 採否：
```
- 利用者が番号で選べるよう、1 件ずつ独立させる。
- 推測で書かない。根拠となる記録の場所を必ず示す。
- 記録の書き方のルール（CLAUDE.md の「書き方のルール」）に沿う。

## 守ること
- `tidy/` 以外のファイルは書き換えない。
- `private/` の中身を案に書き写さない。個人情報・秘密情報を案に書かない。
- 新しい事実を調べて足すことはしない（整理であって調査ではない）。

## 承認されたあと（通常の会話で行う）
1. 承認された案を反映し、各案の「採否」に 採用／見送り／修正して採用 と、利用者の一言を書く。状態を「処理済み」にする。
2. 見送りや修正があれば、その傾向を `tidy/learnings.md` に 1 行で足す（例：「完了した項目でも、記念に残したいものは消さない」）。次回からの案に反映される。
3. Git 管理なら、反映と案のファイルを一緒にコミットする。
